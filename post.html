Unicode、UTF-8、UTF-16，这次终于懂了

从 ASCII 的 128 个字符，到变长编码、代理对、大小端与 BOM 的完整脉络

原文发表于 2021 年 7 月  ·  约 18 分钟  ·  Unicode UTF-8 字节序

你大概率见过这样的场景：一个 JSON 文件在 A 同事的 Mac 上打开正常，传到 B 同事的 Windows 里却变成满屏问号；数据库里明明是「中」，终端里显示成 \xE4\xB8\xAD；emoji 存进 MySQL 直接报错 Incorrect string value。这些问题的根源往往不是程序 bug，而是字符编码这门必修课被跳过了。

01从 ASCII 说起：128 个字符够不够用

计算机最早发端于美国。上世纪，美国人把英文字母、数字和常用符号与二进制位做了统一规定，这就是 ASCII 编码。它用 7 位二进制表示，范围 0x00 - 0x7F，一共 128 个字符，包括大小写字母、数字、标点符号和一些控制字符。

后来计算机扩散到世界各地，不同国家和地区陆续出现了自己的编码：

  • 中国大陆的 GB2312、GBK、GB18030
  • 港台地区的 BIG5
  • 日本的 Shift JIS
  • 韩国的 EUC-KR

同一个二进制数值，在不同编码下会被解释为完全不同的字符，于是「乱码」就成了家常便饭。当互联网打破地域限制后，人们迫切需要一种统一规则来编码世界上所有字符，Unicode 因此诞生。

02Unicode：给全世界的字符发一张身份证

Unicode 是一个国际标准字符集，目标是为世界上每种语言的每个字符分配唯一的编号。它的编码范围是 0x0000 - 0x10FFFF，可以容纳一百多万个字符。

这里的唯一编号通常被称为码点（Code Point）。例如：

  • 大写字母 A 的码点是 U+0041
  • 中文 中 的码点是 U+4E2D
  • 一个老南阿拉伯字母的码点是 U+10A6F

你可以把 Unicode 理解成一本全球字符的「身份证号名册」：它只负责给字符编号，至于这个号码在硬盘里、内存里、网络传输时具体怎么存成字节，那是下一步的事情。

03字符集 ≠ 字符编码：最常被混淆的一组概念

初学编码时最容易把「字符集」和「字符编码」混为一谈，其实它们是两件事。

字符集与字符编码的对比
概念含义例子
字符集 字符的集合，只规定「有哪些字符」 ASCII 字符集、Unicode 字符集、GB2312 字符集
字符编码 把字符集中的字符映射成字节的规则 UTF-8、UTF-16、UTF-32、GBK 编码

Unicode 是一个字符集，而不是字符编码；UTF-8、UTF-16、UTF-32 才是把 Unicode 码点映射为字节的具体编码规则。

04Unicode 只管编号，不管怎么存

Unicode 字符集的编码范围是 0x0000 - 0x10FFFF，理论上最多需要 3 个字节就能表示。

如果简单粗暴地让所有字符都用 3 个字节存储，那么大量只需要 1 个字节的 ASCII 字符就会白白浪费 2 个字节，一份英文文本的体积会膨胀到原来的三倍。这在 20 世纪 90 年代的带宽和存储条件下是不可接受的。

于是 Unicode 提供了多种存储方案，最常见的三种是：

  • UTF-8：变长，1 到 4 个字节，兼容 ASCII
  • UTF-16：变长，2 或 4 个字节
  • UTF-32：定长，固定 4 个字节

名字里的 UTF 是 Unicode Transformation Format 的缩写，后面的数字表示这种编码「至少」需要多少个二进制位来存一个字符。例如 UTF-8 最少 8 位，UTF-16 最少 16 位，UTF-32 最少 32 位。

05UTF-8：变长的艺术

UTF-8 是一种非常流行的变长编码，它把一个码点编码成 1 到 4 个字节，具体长度取决于码点的二进制位数。

5.1 编码规则

  1. 对于单字节字符，字节最高位设为 0，其余 7 位放码点。因此英文字母的 UTF-8 编码与 ASCII 完全相同。
  2. 对于 n 字节字符（n > 1），第一个字节的前 n 位设为 1，第 n+1 位设为 0；后续每个字节的前两位固定为 10；剩下的位按顺序填入码点的二进制。
Unicode 码点范围与 UTF-8 编码模板
Unicode 码点范围（十六进制） UTF-8 二进制模板 字节数
000000 - 00007F 0xxxxxxx 1
000080 - 0007FF 110xxxxx 10xxxxxx 2
000800 - 00FFFF 1110xxxx 10xxxxxx 10xxxxxx 3
010000 - 10FFFF 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx 4

模板中红色的 1 和 0 是固定前缀，x 表示可填入码点数据的位。解码时，只要看第一个字节开头有几个连续的 1，就能知道当前字符占几个字节。

5.2 手算「中」字的 UTF-8

中 的码点是 U+4E2D，二进制为 0100 1110 0010 1101，落在第三行范围，需要用 3 个字节。

① 查表：码点 U+4E2D 的二进制（16 位）

0100 1110 0010 1101 U+4E2D

② 套进三字节模板 1110xxxx 10xxxxxx 10xxxxxx，从低位开始回填

1110 0100 10 111000 10 101101 E4 B8 AD
固定前缀位 码点数据位

最终得到 中 的 UTF-8 编码为 E4 B8 AD。

06UTF-16：直通与代理对

UTF-16 也是一种变长编码，但它只使用 2 字节或 4 字节。

  1. 对于码点小于 0x10000 的字符，直接用 2 个字节存储，数值与码点相同。
  2. 对于码点在 0x10000 - 0x10FFFF 之间的字符，用 4 个字节存储，分为高代理和低代理两个 16 位码元。高代理的前 6 位固定为 110110，低代理的前 6 位固定为 110111；剩下的 20 位存 码点 - 0x10000 的结果。
  3. 大于 0x10FFFF 的码点无法用 UTF-16 表示。
Unicode 码点范围与 UTF-16 编码模板
Unicode 码点范围（十六进制） UTF-16 模板 字节数
00000000 - 0000FFFF xxxxxxxx xxxxxxxx 2
00010000 - 0010FFFF 110110yy yyyyyyyy 110111xx xxxxxxxx 4

因为 中 的码点 0x4E2D 小于 0x10000，所以它的 UTF-16 编码就是 4E 2D。我们用一个增补平面的字符 U+10A6F（老南阿拉伯字母）来展示 4 字节编码过程。

6.1 手算 U+10A6F 的 UTF-16

① 原码点：0x10A6F → 二进制（17 位）

10000 10100 11011 11 0x10A6F

② 减去 0x10000 得到 0x0A6F → 20 位二进制

0000000010 1001101111 高10位=2 / 低10位=0x26F

③ 高 10 位填入高代理 110110，低 10 位填入低代理 110111

110110 00000000010 110111 1001101111 D8 02 / DE 6F
固定前缀位 码点数据位

所以 U+10A6F 的 UTF-16 编码是 D8 02 DE 6F。这也是 JavaScript 里 "\u{10A6F}".length 等于 2 的原因：JS 字符串按 UTF-16 码元计数，而不是按 Unicode 码点计数。

07UTF-32：用空间换时间

UTF-32 是定长编码，每个字符始终占用 4 个字节，直接存储 Unicode 码点，不需要任何转换。

例如 中 的 UTF-32 编码就是 00 00 4E 2D。它浪费空间，但定位第 N 个字符时非常方便：直接用偏移量 N × 4 计算即可。

08三种编码怎么互相转换

UTF-8、UTF-16、UTF-32 都是 Unicode 码点的不同字节表示。只要知道其中一种编码的字节序列，就可以先还原出 Unicode 码点，再用另一种编码规则重新打包。

核心思路：各种 UTF 编码 ↔ Unicode 码点 ↔ 另一种 UTF 编码。

因此，字符集相同（都是 Unicode）是转换可行的前提。如果是 GBK 与 UTF-8 之间的转换，由于字符集不同，必须先通过「字符」做中转：GBK 字节 → 字符 → Unicode 码点 → UTF-8 字节。

10字节序：4E 2D 还是 2D 4E

当最小编码单元是多字节时，就会出现字节序问题。UTF-8 的最小单元是 1 个字节，所以没有字节序问题；UTF-16 和 UTF-32 的最小单元分别是 2 字节和 4 字节，必须先确定高低字节的排列顺序。

  • 大端序（Big-Endian，BE）：高位字节在前，低位字节在后。
  • 小端序（Little-Endian，LE）：低位字节在前，高位字节在后。

以 U+4E2D 为例，它的高位字节是 4E，低位字节是 2D：

11BOM：写在文件开头的标记

BOM（Byte Order Mark，字节顺序标记）是一个特殊的 Unicode 字符 U+FEFF，又被称为「零宽度非换行空格」。它常被放在文件开头，用来告诉读取方文件使用了哪种 UTF 编码以及字节序。

常见 UTF 编码的 BOM
UTF 编码BOM 字节序列
UTF-8EF BB BF
UTF-16LEFF FE
UTF-16BEFE FF
UTF-32LEFF FE 00 00
UTF-32BE00 00 FE FF

UTF-8 本身没有字节序问题，但带 BOM 的 UTF-8 文件仍用 EF BB BF 来标识自己是 UTF-8。很多 Unix 工具不喜欢文件开头多出的这三个字节，因此 Linux 世界通常推荐使用无 BOM 的 UTF-8。

12实战踩坑：Redis 与 MySQL

12.1 Redis 中文 key 显示乱码

向 Redis 写入中文 key 后，在 redis-cli 里查看可能会看到转义序列，而不是汉字。这是因为默认情况下 redis-cli 为了兼容非 UTF-8 终端，会对不可打印字节做转义输出。

解决方法是使用 --raw 参数启动客户端：

redis-cli --raw
GET 中
# 或者
redis-cli --raw GET 中

加上 --raw 后，终端会原样输出 UTF-8 字节，配合支持 UTF-8 的终端就能看到正确的中文。

12.2 MySQL 的 utf8 不是真正的 UTF-8

MySQL 中的 utf8 字符集实际上最多只支持每个字符 3 个字节，因此它无法表示需要 4 个字节的字符，例如 emoji 或码点大于 0xFFFF 的字符。

真正的 UTF-8 在 MySQL 里叫 utf8mb4，其中 mb4 表示 max bytes 4。

假设有一张使用 utf8 字符集的表：

CREATE TABLE `test` (
  `name` char(32) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

插入 中 可以成功，但插入 U+10A6F 的字符会报错：

ERROR 1366 (HY000): Incorrect string value:
'\xF0\x90\xA9\xAF' for column 'name' at row 1

\xF0\x90\xA9\xAF 正是 U+10A6F 的 UTF-8 编码，占 4 个字节，超出了 utf8 的能力范围。

把表改成 utf8mb4 即可解决：

ALTER TABLE test
  CONVERT TO CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
提示：测试时可以用 SET NAMES utf8mb4; 临时修改当前会话的客户端编码，让它与服务器一致。生产环境则应该在 my.cnf 里统一配置服务端和客户端字符集。

14小结

  • ASCII 只能编码 128 个字符，无法覆盖全球文字，于是诞生了 Unicode。
  • Unicode 是字符集，只给字符发号；UTF-8 / UTF-16 / UTF-32 才是字符编码，负责把码点变成字节。
  • UTF-8 是变长 1 - 4 字节编码，兼容 ASCII，是互联网的事实标准。
  • UTF-16 用 2 或 4 字节，超过 BMP 的字符需要高、低代理对。
  • UTF-32 是定长 4 字节，简单直接但浪费空间。
  • UTF-16 / UTF-32 需要考虑字节序，文件开头可以用 BOM 标记。
  • MySQL 的 utf8 是假的 UTF-8，真正支持 4 字节的是 utf8mb4。
只要记住一条：字符集决定「是什么字」，字符编码决定「怎么存成字节」。大多数的乱码，都是把这两件事搞混了。
