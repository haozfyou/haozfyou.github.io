exe 与 dll：一个记事本程序为什么要拆成两半

从一个只有两百多行代码的小程序出发，把导出表、动态加载三件套与函数指针讲清楚

2026 年 10 月  ·  约 16 分钟  ·  DLL 动态链接 函数指针

经常有人问：为什么 Windows 上的程序动不动就是「一个 exe 加一堆 dll」？为什么有的程序删掉一个 dll 直接打不开，有的却只是少了个功能？这篇文章用一个人人都能读完的小例子回答它——一个终端里的记事本程序，源代码被拆成 journal.c 和 journal_core.c 两个文件，编译后分别变成 journal.exe 和 journal_core.dll。看完你会明白这两半各自负责什么、靠什么对上暗号，以及 LoadLibrary / GetProcAddress 这两行代码背后究竟发生了什么。

01先看它长什么样：两个文件，一个程序

这个记事本程序的功能非常简单：新建一篇笔记（标题 + 正文 + 可选的一张配图）、查看某一篇、列出今天写过哪些、删除某一篇。它的源代码只有两个文件：

  • journal.c：约 100 行，只负责和用户打交道——画菜单、读键盘输入、把用户的意图转成一次函数调用。
  • journal_core.c：约 140 行，负责真正干活——取日期、建目录、写文件、复制图片、列出目录。

用 MinGW-w64 的 gcc，两条命令就得到了两个产物：

gcc -shared -o journal_core.dll journal_core.c
gcc -o journal.exe journal.c

-shared 告诉 gcc 输出一个动态链接库。于是 journal_core.c 变成了 journal_core.dll；journal.c 则变成一个只有几十 KB 的可执行文件，因为它自己一行文件操作代码都没有。

运行时，程序会按「日期 / 标题」的层级把笔记存到磁盘上：

2026-10-14\
└── 第一篇笔记\
    ├── content.txt
    └── cover.png

其中 content.txt 的内容是三个字段：

Title: 第一篇笔记
Date: 2026-10-14
Body: 今天搞懂了 exe 和 dll 的分工

接下来我们把这两个文件拆开看。先看 exe 里的 main——它短得有点不像一个完整的程序：

int main(void) {
    HMODULE h = LoadLibraryA("journal_core.dll");
    if (!h) {
        printf("Error loading DLL: %lu\n", GetLastError());
        return 1;
    }

    j_init   = (InitFunc)GetProcAddress(h, "journal_init");
    j_add    = (AddFunc)GetProcAddress(h, "journal_add");
    j_view   = (ViewFunc)GetProcAddress(h, "journal_view");
    j_list   = (ListFunc)GetProcAddress(h, "journal_list");
    j_delete = (DeleteFunc)GetProcAddress(h, "journal_delete");

    if (!j_init || !j_add || !j_view || !j_list || !j_delete) {
        printf("Error: missing symbols\n");
        return 1;
    }

    j_init();
    /* ...菜单循环... */
}

三个疑问随之而来：为什么需要一个 LoadLibraryA？GetProcAddress 在查什么？那些还没定义过、就先用起来的 j_add 又是什么？这段 main 的完整上下文，见文末第 14 节附录。

02用别人的代码，有三种方式

在回答上面的问题之前，先把「一个程序怎么用上别人写好的代码」这件事理清楚。Windows 上主要有三条路：

三种链接方式的对比
方式什么时候绑定交付形态典型场景
静态库（lib*.a） 编译链接期 目标代码被复制进 exe，只需交付一个文件 基础算法库、只在一个程序里用的工具函数
DLL + 隐式链接 进程启动时由加载器自动完成 exe 里只留一张「导入表」，运行时靠导入库（lib*.a）里记下的名字去找 DLL 系统 API、必须在启动前就绪的功能
DLL + 显式加载 运行期，由程序自己决定 不需要导入库，用 LoadLibrary 现场查名字 插件、可选功能、延迟加载

这个记事本走的是第三条路：显式加载。它带来四个立竿见影的好处：

  • 复用——一份 journal_core.dll 可以被图形界面版、命令行版、脚本版同时使用，实现只写一遍。
  • 可替换——改进了存储逻辑，只要导出函数签名不变，重新编译 DLL 即可，exe 完全不用动。
  • 按需加载——用不到的功能可以不加载，也就不占内存、不会被载入进程地址空间。
  • 分工与编译速度——界面逻辑和业务逻辑分开编译，改一处只重编一处。

理解了「什么时候绑定」，剩下的一切都顺理成章：所谓 DLL，就是一份可以被多个进程共享、在运行期才装进地址空间的代码模块。

03DLL 那一侧：把函数写进导出表

DLL 要能被外部找到，就必须先把函数「挂牌公示」。在 Windows 上做这件事的语法是在函数前加 __declspec(dllexport)：

__declspec(dllexport)
int journal_init(void) {
    printf("[Journal] Initialized.\n");
    return 0;
}

__declspec(dllexport)
int journal_add(const char* title, const char* body, const char* image_path) {
    /* 建目录、写 content.txt、复制图片 */
}

这个修饰符不会改变函数的行为，它只是让链接器把函数名连同所在的地址写进 DLL 的导出表（Export Table）。外部程序拿到的，就是这张表。这个 DLL 一共挂出了五个函数：

journal_core.dll 的五个导出函数
导出名签名职责
journal_initint (void)初始化，打印一行启动日志
journal_addint (const char*, const char*, const char*)新建笔记：标题、正文、图片路径
journal_viewint (const char*)查看某篇笔记的 content.txt
journal_listint (void)列出当天写过哪些笔记
journal_deleteint (const char*)删除某篇笔记的整个目录

这张表可以直接看。MinGW 自带 binutils，用 objdump -p 就能把导出表打印出来（下面是 GCC 16.1 / MinGW-w64 上的真实输出，为节省篇幅省略了若干行，地址与时间戳随编译而变）：

        Export Address Table            00000005
        [Name Pointer/Ordinal] Table    00000005

        [   0] +base[   1]  0000 journal_add

        [   2] +base[   3]  0002 journal_init

RVA 是相对虚拟地址，加上模块的基址就是函数在内存里的真实位置。上面这份是 64 位下的结果，五个名字干干净净，可以直接拿去 GetProcAddress；换到 32 位就没这么省心了：gcc 与 GNU ld 沿用 i386 PE 的老规矩，__cdecl 的函数在符号表里带一个前导下划线（_journal_add），__stdcall 还要再加 @ 和参数字节数（_journal_add@12），导出时通常也会一并保留去掉下划线的原名。这就是所谓的名称修饰（name decoration）。

提示：GetProcAddress 是按名字精确匹配的，大小写敏感。如果它一直返回 NULL，先看 objdump -p 打印出来的真实导出名；MinGW 里还可以用 gendef journal_core.dll 直接导出一份 .def 文件，导出清单看得更清楚，也正好可以用它核对该给 GetProcAddress 传什么字符串、或反过来当作链接时的导出别名定义。

04EXE 那一侧：加载三件套

exe 要使用这张导出表，靠的是三个 API，习惯上叫「加载三件套」：

动态加载的三个 API
函数做什么返回失败表现
LoadLibraryA 按名字找到 DLL 并把它映射进当前进程 HMODULE NULL（错误码 126 = 找不到模块）
GetProcAddress 在导出表里按名字查出函数的地址 FARPROC NULL
FreeLibrary 引用计数减一，归零时卸载模块 BOOL FALSE

4.1 HMODULE 是什么

LoadLibraryA 返回的 HMODULE 是一个模块句柄。在 Windows 里，句柄本质上就是一个地址：HMODULE 就是这块 DLL 被装进当前进程地址空间后的基址。后续所有对模块的查询（导出表、资源、导入表）都要带着这个句柄。

它只给文件名、不给完整路径，所以加载器会按一套搜索顺序去找：先是 exe 所在的目录，然后是系统目录，再是 PATH 里的目录。这也是为什么习惯上要求把 DLL 和 exe 放在同一个目录——同时也是为什么「往别人程序旁边塞一个同名 DLL」这种事需要警惕。

4.2 取到的地址要先存起来

GetProcAddress 返回的是一串地址，想调用它就必须先存进一个函数指针。exe 里正是这么做的：五个 static 全局变量在文件开头声明，main 里一次性填充：

static InitFunc   j_init;
static AddFunc    j_add;
static ViewFunc   j_view;
static ListFunc   j_list;
static DeleteFunc j_delete;

从这里开始，j_add("标题", "正文", "图片.png") 写起来和一个普通函数调用没有任何区别——尽管这个函数根本不在 exe 里，而是在另一个文件、另一个模块、另一段内存里。

两个容易忽略的细节：DLL 被映射的那一刻，加载器会调用它自己的入口函数 DllMain；而 DLL 里的 printf 会直接打印到 exe 的控制台上，因为两者共用同一个进程、同一套标准句柄。

06函数指针：typedef 到底该怎么读

整段代码里最容易看晕的就是开头那几行：

typedef int (*InitFunc)(void);
typedef int (*AddFunc)(const char*, const char*, const char*);
typedef int (*ViewFunc)(const char*);
typedef int (*ListFunc)(void);
typedef int (*DeleteFunc)(const char*);

读这类声明的口诀是由内向外：先抓住名字，看紧挨着它的符号，再一层层往外剥。以 AddFunc 为例：

  1. 名字右边是 (const char*, const char*, const char*)，带圆括号，说明这是一个函数的参数表。
  2. 名字左边是 *，说明这个函数名其实是一个指针。
  3. 最左边的 int 是返回类型。

所以 AddFunc 是「指向一个接收三个字符串、返回 int 的函数的指针」这个类型的别名。往后写 AddFunc j_add; 就等价于写 int (*j_add)(const char*, const char*, const char*);——后者一旦嵌套几层就没人看得懂了，这正是 typedef 存在的意义。

接下来那个转换就顺理成章了：

j_add = (AddFunc)GetProcAddress(h, "journal_add");

GetProcAddress 的返回类型是 FARPROC，一个「不带签名信息」的通用函数指针。C 语言不允许把一个函数指针随意赋给另一种类型的函数指针，所以必须显式转换。转换之后的类型才是编译器生成调用代码的依据：它会按 AddFunc 的调用约定去压栈、去取返回值。

注意：函数指针的类型必须和 DLL 里实际导出的函数完全一致，包括调用约定。在 32 位下，__cdecl 由调用方清理栈、__stdcall 由被调用方清理栈，用错约定会导致栈失衡甚至崩溃；64 位下 Windows 只保留了一种调用约定，这个问题才不再出现。

07取不到符号，就别往下走

注意 exe 的写法：五个函数一次性全部取出，然后统一检查，任何一个为 NULL 就立刻报错退出。

这样做有两个好处。一是快速失败：DLL 少了函数、名字写错、版本不对，程序在启动瞬间就会告诉你 Error: missing symbols，而不是等用户点了「2. View note」才莫名其妙地崩溃。二是调用点干净：既然进来之前已经验证过，后面每一次 j_view(title) 都不必再判空，可读性反而更好。

顺带还有一个容易被跳过的细节，藏在 main 的后半段：

setvbuf(stdout, NULL, _IONBF, 0);

这行代码把标准输出改成不缓冲。原因和 DLL 有关：exe 与 DLL 如果链接了不同版本的 C 运行时，就会各自维护一份 stdout 缓冲区，两边交替 printf 时输出的先后顺序可能错乱，甚至内容丢失。关掉缓冲能绕开这个坑；更规范的做法是让 exe 和 DLL 使用同一套 CRT，或者干脆不在库里直接打印日志。

08主程序里的输入：128 / 1024 / 512 三个数字

看回 exe 的菜单循环，有三个缓冲区声明和一个去换行的小技巧：

char title[128], body[1024], image[512];
int choice;

while (1) {
    show_menu();
    if (scanf("%d", &choice) != 1) break;
    getchar();

    if (choice == 1) {
        printf("Title: ");
        if (!fgets(title, sizeof(title), stdin)) break;
        title[strcspn(title, "\n")] = 0;
        /* body、image 同理 */
    }
}
  • fgets(buf, sizeof(buf), stdin)：读一行，最多读 sizeof(buf) - 1 个字符，剩下的位置留给结尾的 '\0'。长度上限是写死在参数里的，读多少都不会越界——这也是为什么永远不要用无长度的 gets。
  • getchar()：读走一个字符。因为 scanf("%d") 只消费数字，用户敲下的那个回车会留在输入缓冲区里；如果不先把它吃掉，紧接着的 fgets 会立刻读到这个换行符，标题就变成了空字符串。这是 scanf 与 fgets 混用时的经典陷阱。
  • title[strcspn(title, "\n")] = 0;：strcspn 返回「第一个出现在第二个参数里的字符」的下标，也就是换行符 '\n' 的位置；把那个位置写成 '\0'，就等于手工去掉了行尾换行。如果这一行恰好长得被截断了、没有换行符，它返回的就是字符串长度，把结尾符再写一遍 0 同样无害。

最后别忘了：这个 title 不只是拿来显示的，它会被 DLL 当作目录名使用。目录名里含有 \ / : * ? " < > | 这些字符时，CreateDirectoryA 会失败，随后 fopen 也会失败，程序只会打印一行 Error: cannot create note file. 一个稍微像样的实现，应该在这里加上非法字符过滤。

09DLL 里的实现：日期、目录、文件

换到 DLL 这一侧，逻辑就朴实多了。先取当天日期：

static void get_date(char* buf, size_t size) {
    SYSTEMTIME st;
    GetLocalTime(&st);
    snprintf(buf, size, "%04d-%02d-%02d", st.wYear, st.wMonth, st.wDay);
}

然后把它当目录名，一层层建下去，再写文件——每一步都检查返回值：

get_date(date, sizeof(date));
CreateDirectoryA(date, NULL);                  /* 2026-10-14\ */

snprintf(note_dir, sizeof(note_dir), "%s\\%s", date, title);
CreateDirectoryA(note_dir, NULL);              /* 2026-10-14\第一篇笔记\ */

snprintf(note_file, sizeof(note_file), "%s\\content.txt", note_dir);
f = fopen(note_file, "w");
if (!f) {
    printf("Error: cannot create note file.\n");
    return -1;
}
fprintf(f, "Title: %s\n", title);
fprintf(f, "Date: %s\n", date);
fprintf(f, "Body: %s\n", body ? body : "");
fclose(f);

这里的 snprintf 值得单独说一句：它接收一个长度参数，写不下就截断，绝不像 sprintf 那样一路写下去。凡是拼接路径、拼接命令的地方，都该用它。

查看、列出、删除三个功能则更短——它们没有直接调用 Win32 API，而是拼出一条命令行交给 system()：

/* journal_view */
snprintf(note_file, sizeof(note_file), "%s\\%s\\content.txt", date, title);
snprintf(cmd, sizeof(cmd), "type \"%s\" 2>nul", note_file);
return system(cmd);

/* journal_list */
snprintf(cmd, sizeof(cmd), "dir \"%s\" 2>nul", date);
return system(cmd);

/* journal_delete */
snprintf(cmd, sizeof(cmd), "rmdir /S /Q \"%s\" 2>nul", note_dir);
return system(cmd);

复制图片同理，先取出文件名，再用 copy /Y：

static void copy_image(const char* note_dir, const char* img_path) {
    char cmd[MAX_PATH_LEN * 2];
    char dst[MAX_PATH_LEN];

    const char* filename = strrchr(img_path, '\\');
    if (!filename) filename = strrchr(img_path, '/');
    filename = filename ? filename + 1 : img_path;

    snprintf(dst, sizeof(dst), "%s\\%s", note_dir, filename);
    snprintf(cmd, sizeof(cmd), "copy /Y \"%s\" \"%s\" >nul", img_path, dst);
    system(cmd);
}
提示：用 system() 拼命令行是「入门友好」的写法，它每次都会额外拉起一个 cmd.exe；而且参数里一旦出现引号、& 之类的字符，拼接结果就可能和你以为的不一样。正式项目里建议换成 CopyFileA、FindFirstFile、SHFileOperation 这类 API，让参数以参数的形式传递，而不是以文本的形式拼进命令行。

最后，DLL 还需一个入口函数 DllMain。它在 DLL 被映射进进程（DLL_PROCESS_ATTACH）、从进程卸载（DLL_PROCESS_DETACH），以及进程里创建、销毁线程时被加载器调用。这个例子什么都不用做，所以直接返回 TRUE：

BOOL WINAPI DllMain(HINSTANCE h, DWORD reason, LPVOID reserved) {
    (void)h; (void)reason; (void)reserved;
    return TRUE;
}

10顺带一提：content.txt 里存的是什么编码

程序把笔记写进 content.txt 时用的是 fopen(..., "w") 加 fprintf，全程只按字节搬运，不做任何编码转换。这意味着文件里到底是什么编码，取决于字符串从哪来：

  • 写进文件的中文，来自用户在控制台的输入，而控制台的编码由代码页决定。中文 Windows 默认是 936（GBK），此时 content.txt 就是 GBK 编码。
  • 如果先在终端里执行 chcp 65001 切到 UTF-8 代码页，同样的操作写出来的就是 UTF-8 字节。

于是就会出现熟悉的一幕：用「ANSI」方式打开一个 UTF-8 的笔记是乱码，用 UTF-8 打开一个 GBK 的笔记也是乱码。journal_list 里那句 dir 的输出也是同理——命令行的输出编码跟着控制台的代码页走。把这两件事联系起来，「乱码」就不再神秘了：它只是字节和解释方式对不上而已。

延伸阅读：关于字符集、码点、UTF-8 / UTF-16 的字节结构和 BOM，见本站第一篇 《Unicode、UTF-8、UTF-16，这次终于懂了》。

11动手验证

这段代码很短，值得亲手跑一遍。把 journal.c 和 journal_core.c 放在同一个目录里，打开装了 MinGW-w64 的命令行（MSYS2 的 MINGW64 / UCRT64 shell，或把 gcc 加进 PATH 的 cmd、PowerShell 都行），进入该目录后：

gcc -shared -o journal_core.dll journal_core.c
gcc -o journal.exe journal.c
journal.exe

11.1 不想自己编译 DLL：直接下载

如果只想验证 exe 这一侧，可以跳过第一条编译命令，取一份已经编译好的 journal_core.dll，把它和 journal.exe 放进同一个目录：

curl -LO https://haozfyou.github.io/journal_core.dll

用浏览器打开 https://haozfyou.github.io/journal_core.dll 同样可以下载。放好之后直接运行 journal.exe 即可，也可以顺手对它执行一次 objdump -p，核对第 03 节列出的那五个导出函数。别忘了它必须和 exe 在同一层目录里——回顾第 04 节，LoadLibraryA 只给了文件名，加载器的搜索以 exe 所在目录为起点。

运行后按提示新建一篇笔记，然后回到命令行观察它落盘的结果：

> dir /b

11.2 用 objdump 看清两个文件的关系

> objdump -p journal_core.dll
> objdump -p journal.exe | findstr /i "DLL Name"

第一条命令打印的正是第 03 节那张导出表；第二条把导入表里的 DLL 依赖挑出来（findstr 是 cmd 的写法，在 MSYS2 / Git Bash 里换成 objdump -p journal.exe | grep "DLL Name" 即可）。实测 MinGW-w64（UCRT 运行库）编出的 journal.exe，结果是一串这样的东西：

> objdump -p journal.exe | findstr /i "DLL Name"

        DLL Name: KERNEL32.dll
        DLL Name: api-ms-win-crt-runtime-l1-1-0.dll
        DLL Name: api-ms-win-crt-stdio-l1-1-0.dll
        DLL Name: api-ms-win-crt-heap-l1-1-0.dll
        ...

换成传统的 msvcrt 版工具链，这一串会变成 msvcrt.dll 加 libgcc_s_*.dll 之类。但这里的关键不是看到哪些系统 DLL，而是不会出现 journal_core.dll：它走的是显式加载，DLL 名字只以字符串的形式存在于代码里，链接器和加载器在程序启动时都不知道它的存在——这正是「显式」二字的含义。

11.3 两个小实验

实验一：把 DLL 改名。执行 ren journal_core.dll journal_core.bak.dll 后再运行 exe，会立刻看到 Error loading DLL: 126。126 就是 ERROR_MOD_NOT_FOUND——模块找不到。

实验二：把 DLL 挪到别的目录。比如把它移到 D:\tmp\ 再运行 exe，同样是 126。因为只给了文件名没给路径，搜索范围以 exe 所在目录为起点。想跨目录加载，就得传完整路径。

13小结

  • 用别人的代码有三种方式：静态库在链接期复制代码，隐式链接在启动时由加载器装 DLL，显式加载在运行期自己查名字。
  • __declspec(dllexport) 的作用是把函数写进 DLL 的导出表，导出表就是 DLL 对外的「挂牌公示」。
  • LoadLibraryA 返回的 HMODULE 是 DLL 在进程中的基址；GetProcAddress 在导出表里按名字取地址；FreeLibrary 用引用计数决定何时真正卸载。
  • 取回来的地址必须存进函数指针，而函数指针的类型（参数、返回类型、调用约定）必须和 DLL 里的实现严格一致。
  • 读 typedef int (*Fn)(...) 的口诀是由内向外：名字 → 右边参数表 → 左边指针 → 最左返回类型。
  • fgets 带长度上限、snprintf 带长度上限、strcspn 去换行、scanf 之后补一个 getchar——这些小细节决定了程序是「能跑」还是「稳」。
一句话记住这个结构：exe 负责和用户说话，dll 负责和系统说话，连接它们的是「一句字符串名字」和「一个存着地址的函数指针」。理解了这层关系，再看 Windows 上任何一个 exe 加一堆 dll 的程序，结构就清晰了。

14附录：主程序 journal.c 完整源码

下面是 exe 一侧的全部代码，共 97 行，与第 01、04、06、07、08 节引用的片段完全一致。它只做三件事：加载 DLL、取回五个函数地址、把菜单选择转成一次调用——所有与文件、目录打交道的工作都在 DLL 里。

如有需要请在temp里新建文件，写入这个程序，方便学习。同时如果你已经搭建好了，可以创建一个新笔记，输入全部使用debug来作为调试，也方便后续区分

// journal.c
// 编译：gcc -o journal.exe journal.c

#include <stdio.h>
#include <string.h>
#include <windows.h>

typedef int (*InitFunc)(void);
typedef int (*AddFunc)(const char*, const char*, const char*);
typedef int (*ViewFunc)(const char*);
typedef int (*ListFunc)(void);
typedef int (*DeleteFunc)(const char*);

static InitFunc   j_init;
static AddFunc    j_add;
static ViewFunc   j_view;
static ListFunc   j_list;
static DeleteFunc j_delete;

static void show_menu(void) {
    printf("\n=== Journal Manager v2.0 ===\n");
    printf("1. New note\n");
    printf("2. View note\n");
    printf("3. List today's notes\n");
    printf("4. Delete note\n");
    printf("5. Exit\n");
    printf("Choice: ");
}

int main(void) {
    HMODULE h = LoadLibraryA("journal_core.dll");
    if (!h) {
        printf("Error loading DLL: %lu\n", GetLastError());
        return 1;
    }

    j_init   = (InitFunc)GetProcAddress(h, "journal_init");
    j_add    = (AddFunc)GetProcAddress(h, "journal_add");
    j_view   = (ViewFunc)GetProcAddress(h, "journal_view");
    j_list   = (ListFunc)GetProcAddress(h, "journal_list");
    j_delete = (DeleteFunc)GetProcAddress(h, "journal_delete");

    if (!j_init || !j_add || !j_view || !j_list || !j_delete) {
        printf("Error: missing symbols\n");
        return 1;
    }

    j_init();

    char title[128], body[1024], image[512];
    int choice;

    setvbuf(stdout, NULL, _IONBF, 0);

    while (1) {
        show_menu();
        if (scanf("%d", &choice) != 1) break;
        getchar();

        switch (choice) {
            case 1:
                printf("Title: ");
                if (!fgets(title, sizeof(title), stdin)) break;
                title[strcspn(title, "\n")] = 0;
                printf("Body: ");
                if (!fgets(body, sizeof(body), stdin)) break;
                body[strcspn(body, "\n")] = 0;
                printf("Image (optional, Enter to skip): ");
                if (!fgets(image, sizeof(image), stdin)) break;
                image[strcspn(image, "\n")] = 0;
                j_add(title, body, image);
                break;
            case 2:
                printf("Title: ");
                if (!fgets(title, sizeof(title), stdin)) break;
                title[strcspn(title, "\n")] = 0;
                j_view(title);
                break;
            case 3:
                j_list();
                break;
            case 4:
                printf("Title: ");
                if (!fgets(title, sizeof(title), stdin)) break;
                title[strcspn(title, "\n")] = 0;
                j_delete(title);
                break;
            case 5:
                printf("Bye.\n");
                FreeLibrary(h);
                return 0;
        }
    }

    FreeLibrary(h);
    return 0;
}
